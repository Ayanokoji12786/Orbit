# Account deletion worker deployment

This runbook applies only to an isolated **Orbit** Supabase project. The source and local SQL tests prepare an unattended retry path, but it is not active until the deployment and hosted checks below pass. Do not run these steps against the unrelated connected project.

1. Apply the Orbit migrations in order, including `20261011120000_account_deletion_worker.sql`, and deploy both `delete-account` and `delete-account-worker`. The worker has `verify_jwt = false` because its handler verifies a dedicated HMAC; confirm that configuration on the deployed function.
2. Enable `pg_cron`, `pg_net`, and `pgcrypto` in the Orbit database. Create two Vault secrets through the Supabase Dashboard: `orbit_account_deletion_worker_url` contains the full **Orbit** HTTPS URL ending `/functions/v1/delete-account-worker`; `orbit_account_deletion_worker_secret` contains a newly generated random secret of at least 32 characters. Set that same signing secret as the Edge Function environment variable `ORBIT_ACCOUNT_DELETION_WORKER_SECRET`. Keep the signing secret separate from the service-role key and never paste either into the Cron command or repository.
3. After verifying the project identity and secret values, run [`install-account-deletion-worker.sql`](../supabase/ops/install-account-deletion-worker.sql) in that project's SQL editor. It schedules one invocation per minute. The job reads Vault at execution time and queues only a timestamp and its HMAC-SHA256 signature; it does not put a reusable key in `pg_net` headers. The signature is for the exact UTF-8 string `orbit-account-deletion-worker:v1:<Unix seconds>`, encoded as lowercase hex. The Edge handler accepts a timestamp within 120 seconds. The request carries no user ID and processes one existing, due deletion tombstone per tick.
4. Inspect the named Cron job and its run history, and check `net._http_response` for HTTP failures. An idle tick should return `{ "claimed": false }`. A direct unsigned request must return 401; a valid signed request must reach the handler. In an isolated test account, start deletion, close the app after a 202, and observe the request row disappear after Auth deletion. Also test a forced function failure, expired lease reclaim, a large Storage library/room, and a lost final HTTP response. Confirm Storage bytes, LiveKit state, and Auth identity are gone. Check that no other account was claimed. The local PGlite tests cannot prove these hosted outcomes.
5. Monitor repeated `next_attempt_at` delays and Cron/Edge errors. Failed slices back off to at most one hour, while partial slices become due after two seconds; the one-minute schedule determines the usual continuation pace. To stop the worker, deactivate or unschedule `orbit-account-deletion-worker` in Supabase Cron. Rotate the Edge secret and matching Vault secret together; a mismatch pauses processing rather than authorizing a request.

`pg_net` may expose queued request headers to database roles that can use it. A captured timestamp/signature can be replayed briefly, but cannot name an account or create a deletion request. Keep Cron and Vault access limited to trusted operators, and inspect the actual project grants before production. The `pg_net` HTTP request queue is unlogged, so a database crash may lose an individual tick; the next minute's tick discovers durable tombstones again. Its default request timeout is two seconds, so the installer sets 120 seconds explicitly.
